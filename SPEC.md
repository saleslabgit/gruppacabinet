# Техническое задание: кабинет психологов

**Платёжный провайдер MVP:** WEBPAY (ООО «ВЕБ ПЭЙ»)

---

# 1. Цель проекта

Разработать отдельное Laravel-приложение — личный кабинет психологов и административную панель для существующего сайта-каталога психологических групп.

Production-адреса фиксированы:

- основной публичный сайт: `https://gruppa.info/`;
- кабинет и административная часть: `https://gruppa.info/cabinet/`.

Кабинет является отдельным Laravel-приложением, но публично доступен в подкаталоге `/cabinet` того же домена. Основной сайт и кабинет имеют разный код и разный жизненный цикл deployment.

Существующий публичный сайт продолжает выполнять функции каталога и содержит:

- форму регистрации психолога;
- формы записи участников в группы.

Новое приложение отвечает за:

- регистрацию и модерацию психологов;
- авторизацию психологов;
- управление группами;
- оплату размещения;
- продление размещения;
- модерацию групп;
- контроль срока размещения;
- получение заявок участников;
- административное управление пользователями, группами, платежами и справочниками.

Автоматическая публикация групп в существующий каталог **не входит в MVP**. Администратор публикует группу вручную и после этого отмечает её активной в кабинете.

## Структура репозитория и граница deployable-приложения

Docker используется только как локальная серверная среда. Laravel-приложение и Docker-инфраструктура **не смешиваются в одном каталоге**.

Обязательная структура верхнего уровня:

```text
project/
├── application/          # самостоятельный Laravel-проект; только его содержимое разворачивается на production
│   ├── app/
│   ├── bootstrap/
│   ├── config/
│   ├── database/
│   ├── public/
│   ├── resources/
│   ├── routes/
│   ├── storage/
│   ├── tests/
│   ├── artisan
│   ├── composer.json
│   └── composer.lock
├── docker/               # только локальная инфраструктура
│   ├── php/
│   ├── web/
│   └── ...
├── compose.yaml
├── docs/
└── README.md
```

Требования:

- `application/` является самостоятельным deployable Laravel-проектом;
- Dockerfile, `compose.yaml`, конфигурации локальных контейнеров и локальные volumes не размещаются внутри `application/`;
- Docker монтирует `./application` в контейнер как bind mount;
- локальные данные MySQL/служебные volumes хранятся вне `application/` либо в Docker named volumes;
- production-код не зависит от Docker-specific hostnames, путей или команд;
- не создаётся вторая вручную синхронизируемая копия Laravel-проекта вроде `deploy/`: источником production-файлов является `application/`;
- при необходимости архив/пакет для SFTP/FTP может автоматически формироваться из `application/`, но такой каталог является build artifact и не редактируется вручную.

## Локальная разработка

Docker Compose окружение имитирует сервер и содержит:

- PHP 8.2;
- MySQL;
- веб-сервер;
- Composer.

Исходный код находится обычными файлами в `application/` на компьютере разработчика и подключается в контейнер.

Проект должен запускаться одной командой из корня репозитория.

Docker в этом проекте решает только задачи локального окружения:

- одинаковая версия PHP и расширений;
- локальный MySQL;
- локальный web-server;
- воспроизводимый запуск команд Composer/Laravel.

Docker **не является способом deployment** и не должен требоваться на production.

## Production и размещение на shared-хостинге

Docker не используется. Production — обычный shared-хостинг/панель с `public_html`.

Основной сайт работает из `public_html` по адресу `https://gruppa.info/`. Кабинет доступен по адресу `https://gruppa.info/cabinet/`, но **полный Laravel-проект нельзя размещать внутри публичной директории**.

Предпочтительная физическая структура:

```text
/home/account/
├── cabinet_app/                 # закрытая часть Laravel, содержимое repository/application/
│   ├── app/
│   ├── bootstrap/
│   ├── config/
│   ├── database/
│   ├── resources/
│   ├── routes/
│   ├── storage/
│   ├── vendor/
│   ├── artisan
│   ├── composer.json
│   └── .env
└── public_html/                 # публичный сайт gruppa.info
    ├── ...                      # существующий основной сайт
    └── cabinet/                 # только публичная часть Laravel
        ├── index.php
        ├── .htaccess
        ├── app.css / css/...
        ├── app.js / js/...
        └── другие публичные assets
```

Допускается эквивалентная структура, которую поддерживает конкретная hosting-панель, но инварианты обязательны:

- Laravel `.env`, `vendor/`, `storage/`, исходники PHP, migrations и конфигурация не доступны из web root напрямую; если hosting-панель не позволяет безопасно разместить закрытую часть Laravel вне `public_html`, production deployment блокируется до выбора безопасной схемы;
- `public_html/cabinet/` содержит только содержимое Laravel `public/` и front controller, настроенный на закрытый `cabinet_app`;
- существующие rewrite rules основного сайта не должны перехватывать `/cabinet/*`; физическая директория `/cabinet` и её `.htaccess` должны корректно обслуживать Laravel;
- production `APP_URL=https://gruppa.info/cabinet`;
- все ссылки, redirects, формы и assets генерируются через Laravel helpers (`route()`, `url()`, `asset()` и т.п.), без захардкоженных путей от корня домена;
- при необходимости используется `ASSET_URL=https://gruppa.info/cabinet`, если это требуется фактической конфигурацией shared-хостинга;
- приложение должно корректно работать именно из base path `/cabinet`, а не только из `/`;
- публичные API-маршруты кабинета имеют полный production URL вида `https://gruppa.info/cabinet/api/v1/...`;
- WEBPAY return/cancel/notify URL также формируются внутри `https://gruppa.info/cabinet/...`.

На сервер разворачивается только содержимое `application/` как обычный Laravel-проект с разделением закрытой и публичной частей согласно схеме выше. Каталог `docker/`, `compose.yaml` и другие файлы локальной инфраструктуры на production не загружаются.

Production:

- PHP 8.2.32 или совместимый;
- MySQL;
- cron используется для Laravel Scheduler;
- supervisor либо доступный shared-hosting механизм/cron используется для обработчика очередей;
- production `.env` создаётся непосредственно на сервере и не хранится в Git;
- `APP_DEBUG=false`;
- WEBPAY production credentials появляются только на финальном production-этапе (§31, этап 16).

## Совместимость окружений

Поскольку разработка ведётся в Docker, а production работает без него, расхождение версий и расширений PHP должно быть исключено на уровне конфигурации:

- в `composer.json` фиксируется `config.platform.php` равным версии production;
- в `composer.json` перечисляются все требуемые расширения PHP в секции `require`;
- перед выкладкой выполняется `composer check-platform-reqs`;
- список требуемых расширений дублируется в инструкции по установке;
- приложение не должно использовать Docker-only особенности файловой системы, DNS или сетевых имён;
- команды установки и запуска production документируются отдельно от локального Docker-запуска.

# 3. Роли

В MVP две роли.

## Администратор

Имеет доступ ко всем данным приложения.

Может:

- просматривать всех психологов;
- создавать психологов вручную;
- редактировать;
- отключать;
- удалять;
- принимать или отклонять анкеты;
- назначать психолога бесплатным/платным;
- просматривать документы психолога;
- просматривать все группы;
- создавать и редактировать группы;
- модерировать группы;
- отправлять группу на доработку;
- отклонять группу;
- одобрять группу;
- отмечать группу опубликованной/активной;
- вручную удалять брошенные черновики;
- просматривать заявки участников;
- просматривать платежи;
- отмечать выполненный возврат платежа;
- управлять справочниками и настройками.

В MVP администратор один, но архитектура не должна препятствовать появлению нескольких администраторов.

Все действия администратора, меняющие статус психолога, группы или платежа, фиксируются с указанием автора действия (см. §4.8).

## Психолог

Может:

- войти в кабинет после одобрения;
- просматривать информацию о себе;
- просматривать свои группы;
- создавать группы;
- редактировать группу на разрешённых этапах;
- удалять черновые/неактивные группы;
- отправлять группу на модерацию;
- оплачивать размещение, если он платный;
- продлевать размещение;
- видеть статус каждой своей группы;
- видеть историю замечаний администратора по своей группе;
- видеть заявки только своих групп;
- отмечать заявку обработанной.

Психолог **не видит раздел истории платежей**. Стоимость и факт оплаты конкретной операции он видит только в рамках самой операции оплаты.

# 4. Основные архитектурные решения

## 4.1. `status` — единственный источник правды

Исходные поля:

- `accept`;
- `disabled`;
- `free`;
- `admin`

можно сохранить в схеме, но **строить workflow на `accept=true/false` запрещено**.

У пользователя и у группы существует явный `status`.

Требования:

- `status` — единственный источник правды о стадии жизненного цикла;
- `accept` не используется в бизнес-логике, условиях, выборках и шаблонах;
- если `accept` сохраняется для совместимости с существующим сайтом, он вычисляется из `status` и записывается **только в одном месте** — в model observer или доменном сервисе;
- контроллеры, формы и seed-данные не имеют права писать `accept` напрямую.

`disabled`, `free` и `admin` остаются отдельными независимыми признаками и не входят в `status`.

## 4.2. Статусы как перечисления и машина состояний

Статусы пользователя, группы и платежа реализуются PHP-enum (backed enum, string) с кастами Laravel.

Для каждого enum описывается допустимость переходов, например метод `canTransitionTo(self $target): bool`.

Требования:

- ни один переход статуса не выполняется присваиванием поля напрямую из контроллера;
- переход выполняется через доменный сервис, который проверяет допустимость перехода и выбрасывает исключение при недопустимом;
- в БД используется строковая колонка (`varchar`), а не MySQL `enum`, чтобы не усложнять миграции;
- допустимый набор значений и матрица переходов покрываются автоматическими тестами.

## 4.3. Удаление

Использовать soft delete для основных сущностей.

Физическое удаление пользователя или группы не должно уничтожать:

- платежи;
- историю заявок;
- историю статусов;
- связанные данные.

## 4.4. Бесплатность группы

`gp_users.free` показывает **текущий тариф психолога** и является источником истины при определении тарифа новой операции, в том числе продления.

При создании группы текущее значение копируется в `gp_groups.free`.

`gp_groups.free` является снимком тарифа на момент создания группы и используется для истории и логики первоначального размещения. Последующая смена тарифа психолога не меняет это поле задним числом.

При продлении `gp_groups.free` **не используется** для определения необходимости оплаты. В момент начала каждой новой попытки продления приложение проверяет актуальное значение `gp_users.free` владельца группы:

- `gp_users.free=true` — продление бесплатное, платёж не создаётся;
- `gp_users.free=false` — продление платное и после подключения WEBPAY требует отдельной оплаты `type=extension`.

Таким образом, если администратор изменил тариф психолога после создания или предыдущего продления группы, следующее продление выполняется уже по новому текущему тарифу.

## 4.5. Оплата

Платёжный провайдер MVP — **WEBPAY**.

Успешный возврат браузера пользователя со страницы WEBPAY (`wsb_return_url`) **не является самостоятельным подтверждением оплаты**.

Доверенными источниками подтверждения являются только серверные данные WEBPAY:

1. валидный нотификатор WEBPAY на `wsb_notify_url` с корректной подписью и совпадающими данными заказа;
2. успешный серверный ответ WEBPAY API `get_transaction`, полученный приложением и проверенный по подписи, сумме, валюте, идентификатору заказа и транзакции.

Browser return/cancel используется только для UX и как повод инициировать серверную проверку. Он не имеет права сам менять платёж в `succeeded`, разблокировать группу или применять продление.

Обработка подтверждения должна быть идемпотентной: повторный нотификатор, повторный API-check или одновременное получение обоих подтверждений не должны повторно менять состояние группы или дважды применять продление.

Оплата в MVP бывает двух типов:

- `placement` — оплата размещения новой группы;
- `extension` — оплата продления размещения существующей группы.

Для MVP используется интернет-эквайринг WEBPAY по банковским картам. ЕРИП, рекуррентные платежи, Apple Pay, карты рассрочки и другие платёжные сценарии не входят в MVP без отдельной задачи.

MVP рассчитан на **одностадийный платёж**, при котором успешная операция финансово завершена. Двухстадийный flow `Authorized → capture/void` приложением не реализуется. До production необходимо убедиться, что WEBPAY-аккаунт настроен соответствующим образом.

## 4.6. Денежные суммы

Все денежные суммы хранятся **целым числом в минорных единицах** (копейках) в колонках типа `unsigned bigint`.

Использование `float` запрещено. `decimal` не используется, чтобы исключить расхождения округления при сверке с банком.

Валюта хранится отдельным полем, значение по умолчанию — `BYN`.

Форматирование для отображения выполняется единым helper/Blade-компонентом.

## 4.7. Дата и время

- в БД всё хранится в UTC;
- `APP_TIMEZONE=UTC`;
- отображение и ввод дат выполняются в `Europe/Minsk`;
- преобразование выполняется единым helper/Blade-компонентом, а не вручную на каждой странице;
- вся логика сроков размещения работает с UTC.

## 4.8. История статусов и аудит

Единственного поля «комментарий модератора» недостаточно: при повторных доработках комментарий будет перезаписан и психолог потеряет предыдущие замечания.

Создаётся таблица `gp_group_status_history`:

- `id`;
- `group_id`;
- `from_status` — nullable;
- `to_status`;
- `actor_id` — кто выполнил переход, nullable для системных переходов;
- `actor_type` — `user` / `system`;
- `comment` — nullable;
- `created_at`.

Каждый переход статуса группы создаёт запись истории в той же транзакции, что и сам переход.

Психолог видит историю замечаний по своей группе.  
Администратор видит полную историю.

Для ключевых административных действий, которые не покрываются историей статусов группы, создаётся минимальный бизнес-аудит `gp_audit_log`:

- `id`;
- `actor_id` — nullable для системных действий;
- `actor_type` — `user` / `system`;
- `entity_type` — стабильный код сущности (`user`, `payment`, `setting` и т.п.);
- `entity_id` — nullable для действий над глобальными настройками;
- `action` — стабильный код действия;
- `metadata` — json, nullable, только необходимые несекретные old/new значения;
- `created_at`.

Минимально фиксируются:

- принятие/отклонение психолога;
- enable/disable психолога;
- смена free/paid;
- soft delete/restore психолога, если restore будет доступен администратору;
- ручная отметка возврата платежа;
- изменение цен и сроков в бизнес-настройках.

Полные анкеты, документы, пароли, секреты, подписи платежей и полные тела запросов в `metadata` не записываются.

## 4.9. Очереди

Отправка писем и обработка отложенных задач выполняются через очередь Laravel на драйвере `database`.

Причина: синхронная отправка писем внутри scheduled-команды приводит к падению всей команды при таймауте SMTP и к потере части уведомлений.

Требования:

- таблица очереди создаётся миграцией;
- таблица `failed_jobs` создаётся миграцией;
- на production обработчик очереди запускается через supervisor либо через cron с `queue:work --stop-when-empty`;
- признак фактической отправки письма проставляется только внутри job после успешной отправки; успешная постановка job в очередь сама по себе не считается отправкой;
- для писем, которые должны отправляться один раз за период, должна быть защита от повторной постановки одинаковой job до завершения первой попытки (см. §27).

## 4.10. Техническое логирование

Не требуется логировать каждое пользовательское действие или полные входящие payload.

В application logs фиксируются только события, необходимые для эксплуатации и разбора ошибок:

- отклонение интеграционного запроса из-за валидации/rate limit/опционального IP allowlist — endpoint, `X-Request-Id`, причина, IP и технический контекст без тела анкеты/файлов;
- критические ошибки очередей и scheduler;
- ошибки обращения к WEBPAY API;
- невалидный нотификатор WEBPAY;
- неизвестный `order_number` / `transaction_id` WEBPAY;
- несовпадение суммы, валюты или заказа при платёжной проверке;
- переход платежа в `succeeded` и ручная отметка `refunded` — по внутреннему `payment_id`/`order_number`, без платёжных секретов;
- системные исключения Laravel стандартным production-логированием.

Не логируются:

- полные тела анкет и заявок;
- содержимое или бинарные данные документов;
- пароли и password reset tokens;
- WEBPAY SecretKey/API password;
- значения подписей целиком;
- полные номера банковских карт, если они когда-либо появятся во входящих данных.

Бизнес-аудит (§4.8) и журнал платёжных нотификаторов (§19) не заменяются application log и не должны без необходимости дублироваться в нём.

# 5. Регистрация психолога

## Сценарий

1. Пользователь заполняет анкету на существующем сайте.
2. Сайт серверным POST-запросом передаёт данные в новое приложение.
3. Создаётся `gp_users`.
4. Пользователь получает статус `pending`.
5. Администратор видит новую анкету.
6. Администратор выбирает: принять или отклонить.
7. При принятии:
   - пользователь получает статус `approved`;
   - на email отправляется одноразовая ссылка установки пароля.
8. Психолог устанавливает пароль.
9. После этого может войти в кабинет.

До принятия войти невозможно.

Администратор должен иметь возможность повторно отправить письмо установки пароля.

## Уникальность email и повторная подача анкеты

Email психолога уникален среди активных (не soft-deleted) записей.

Поведение при поступлении анкеты с уже существующим email определяется статусом существующей записи:

| Статус существующей записи | Поведение |
|---|---|
| `pending` | Данные существующей анкеты обновляются, новые документы добавляются. HTTP 200. |
| `rejected` | Запись возвращается в `pending`, данные обновляются, администратор видит её как новую. HTTP 200. |
| `approved` | Новая анкета не создаётся. HTTP 409 с понятным сообщением. Событие логируется. |
| `disabled=true` | Новая анкета не создаётся. HTTP 409. Событие логируется. |
| soft-deleted, без активной записи с email | Новая анкета создаёт нового психолога в `pending` с новым ID. HTTP 201. Историческая запись и её связи не изменяются. |

На уровне БД уникальность активного email реализуется технической generated column, например `active_email`, которая содержит `email` только при `deleted_at IS NULL`, а для soft-deleted записей — `NULL`. На эту колонку создаётся уникальный индекс.

Это гарантирует, что одновременно может существовать только одна активная запись с конкретным email, но soft-deleted запись не блокирует создание новой записи через публичную анкету или администратором с тем же email.

Техническая generated column не используется в бизнес-логике приложения.

Использовать уникальный индекс `(email, deleted_at)` **запрещено**: в MySQL несколько строк с `NULL` в составе уникального индекса допустимы, поэтому такой индекс не гарантирует уникальность активного email.

Простой уникальный индекс по `email` также использовать нельзя: при soft delete удалённая запись навсегда заблокирует повторное использование адреса.

## Установка пароля

- используется штатный механизм Laravel (password broker), самописные токены не создаются;
- срок жизни ссылки задаётся конфигурацией, по умолчанию 72 часа;
- токен одноразовый, после использования инвалидируется;
- повторная отправка письма администратором инвалидирует предыдущую ссылку;
- на запрос установки пароля и на форму входа устанавливается rate limit.

# 6. Анкета психолога

В `gp_users` хранятся основные данные анкеты:

- фамилия;
- имя;
- отчество;
- телефон;
- email;
- тип образования;
- другое образование;
- номер и срок действия лицензии;
- опыт ведения групп;
- количество проведённых групп;
- подтверждение достоверности документов;
- подтверждение соответствия образования;
- готовность провести вебинар или эфир;
- `personal_data_consent_at` — дата и время согласия на обработку персональных данных;
- `personal_data_consent_version` — версия текста согласия;
- `status`;
- `accept`;
- `disabled`;
- `free`;
- `admin`;
- `password`;
- timestamps;
- soft delete.

Приложение обрабатывает персональные данные психологов, копии дипломов и лицензий, а также ФИО и телефоны участников групп. Факт и версия согласия на обработку персональных данных фиксируются при приёме анкеты. Публичный сайт обязан передавать эти значения вместе с анкетой.

Поскольку администратор хранится в той же таблице, все поля анкеты должны быть nullable, а для администратора обязательными остаются только email, пароль и признак `admin`.

Модель `User` явно указывает `protected $table = 'gp_users';`.

## Дополнительное обучение

Текущие обучения хранятся только в `gp_user_trainings`: `id`, `user_id` (FK на
`gp_users`), `position` (unsigned integer), nullable `modality_program` и
`training_center` (строки до 255), `graduation_year` (unsigned small integer),
`training_hours` (unsigned integer), timestamps. Уникальность `(user_id, position)`;
порядок списка определяется `position`. Допустимо ноль, одно или любое число
обучений без произвольного прикладного лимита. Новая запись содержит хотя бы одно
содержательное значение; ноль для числового поля допустим.

Четыре прежних поля обучения в `gp_users` оставлены только для совместимости:
runtime их не читает, не записывает и не синхронизирует. Добавочная миграция переносит
существующий набор ненулевых legacy-полей в обучение с `position=0`, сохраняя значения
без потерь, в том числе у soft-deleted пользователей. Старые сертификаты связываются
с этим единственным обучением; без него остаются без связи. Миграция обязательна
перед запуском нового кода. Откат не восстанавливает новые множественные обучения
в устаревшие поля; перед откатом требуется сохранить новые данные отдельно.

Администратор создаёт, редактирует, удаляет и упорядочивает блоки обучения в
утверждённой форме. Сохранение анкеты и списка транзакционно; сохраняемые строки
сохраняют ID, чужие ID отклоняются. Карточка и «Мои данные» показывают весь текущий
список в порядке `position`.

## Документы

Документы хранятся отдельной сущностью `gp_user_documents`:

- `id`;
- `user_id`;
- `user_training_id` — nullable FK на `gp_user_trainings`, только для сертификатов;
- `type`;
- `path`;
- `original_name`;
- `mime_type`;
- `size`;
- timestamps.

Типы документов:

- диплом;
- сертификат;
- лицензия / членство;
- свидетельство о государственной регистрации.

Удаление обучения обнуляет связь сертификатов (`ON DELETE SET NULL`), но не
удаляет документы или файлы. У одного обучения может быть несколько сертификатов;
старые несвязанные документы остаются доступны через прежние защищённые маршруты.

Требования к файлам:

- файлы не лежат в публично доступной директории, хранение в `storage/app/private`;
- имя файла на диске генерируется случайным, оригинальное имя хранится в БД отдельным полем;
- проверяется реальный тип содержимого файла, а не расширение;
- допустимые типы: `pdf`, `jpeg`, `png`;
- максимальный размер файла задаётся конфигурацией;
- просмотр и скачивание выполняются через контроллер Laravel после проверки прав доступа (владелец или администратор).

# 7. Статусы психолога

Основные:

### `pending`
Анкета ожидает проверки.

### `approved`
Анкета принята.

### `rejected`
Анкета отклонена.

Допустимые переходы:

- `pending → approved`;
- `pending → rejected`;
- `rejected → pending` (повторная подача анкеты, см. §5);
- `approved → rejected` — не используется, для отключения используется `disabled`.

## Признак `disabled`

`disabled` существует отдельно от `status`.

Если `disabled=true`, пользователь не может войти независимо от его статуса.

**Блокировка действует немедленно, включая уже открытые сессии.**

Требования:

- middleware проверяет `disabled` и статус пользователя на каждом запросе в защищённой зоне;
- при обнаружении блокировки текущая сессия завершается, пользователь разлогинивается с понятным сообщением;
- при установке `disabled=true` администратором все активные сессии пользователя инвалидируются немедленно (смена `remember_token` и/или удаление сессий пользователя из хранилища сессий);
- те же правила действуют при soft delete пользователя и при переводе в `rejected`.

Хранилище сессий — `database`, чтобы инвалидация сессий конкретного пользователя была технически возможна. Соответствующая миграция создаётся на этапе 2.

# 9. Создание бесплатной группы

Если `gp_users.free=true`:

1. Психолог нажимает «Добавить группу».
2. Создаётся черновая группа с `free=true`, статус `draft`.
3. Открывается форма группы.
4. Психолог заполняет данные.
5. Нажимает «Отправить на модерацию».
6. Группа получает статус `moderation`.

Платёж не создаётся.

---

# 10. Создание платной группы

Если `gp_users.free=false` после подключения WEBPAY-этапа:

1. Психолог нажимает «Добавить группу».
2. Создаётся технический черновик `gp_groups` со статусом `awaiting_payment` и `free=false`.
3. Создаётся запись `gp_payments` с типом `placement` и уникальным `order_number` для `wsb_order_num`.
4. Платёж переводится в `pending`, приложение формирует подписанную форму WEBPAY и перенаправляет пользователя на платёжную страницу.
5. WEBPAY возвращает пользователя на `wsb_return_url` либо `wsb_cancel_return_url` и независимо может прислать серверный нотификатор на `wsb_notify_url`.
6. Browser return/cancel сам по себе состояние группы не меняет.
7. При успешном return приложение выполняет серверную проверку `get_transaction`, если для неё достаточно полученных идентификаторов; параллельно/позже может прийти нотификатор.
8. После первого доверенного подтверждения успешной оплаты:
   - платёж получает статус `succeeded`;
   - сохраняется `transaction_id` WEBPAY;
   - группа переходит из `awaiting_payment` в `draft`.
9. Повторный нотификатор или повторный `get_transaction` не повторяет эффект.
10. Пользователю становится доступна форма заполнения группы.
11. После заполнения он отправляет группу на модерацию.
12. Группа получает статус `moderation`.

Если пользователь вернулся с WEBPAY, но серверное подтверждение ещё не получено или временно недоступно, показывать:

**«Оплата подтверждается WEBPAY»**

и кнопку обновления страницы.

Заполнение группы до доверенного подтверждения невозможно.

Если подтверждённая проверка WEBPAY показывает неуспешную/отменённую оплату, продакт-эффект не применяется. Пользователь может повторить оплату; для каждой новой попытки создаётся новая запись платежа с новым `order_number`. Предыдущие записи сохраняются.

`wsb_cancel_return_url` сам по себе не переводит платёж в `cancelled`: отмена/ошибка должна быть подтверждена данными WEBPAY либо платёж остаётся `pending` до проверки.

## Отклонение оплаченной группы и возврат средств

Если оплаченная группа отклонена администратором (`moderation → rejected`):

- указание причины отклонения **обязательно**, причина сохраняется и показывается психологу;
- возврат денежных средств выполняется администратором **вручную через личный кабинет WEBPAY**, автоматический возврат через WEBPAY API в MVP не реализуется;
- в карточке отклонённой группы администратору показывается связанный платёж с `order_number`, `transaction_id`, суммой и датой;
- после фактического выполнения возврата в WEBPAY администратор отмечает платёж возвращённым в приложении: платёж получает статус `refunded`, заполняются `refunded_at` и комментарий;
- отметка о возврате — учётное действие внутри приложения и не отправляет запрос на возврат в WEBPAY;
- действие фиксируется в `gp_audit_log`;
- отклонённая группа не даёт права на бесплатное создание новой: чтобы разместить группу заново, психолог создаёт новую группу и оплачивает её как обычно.

## Брошенные черновики

Черновики в статусах `awaiting_payment` и `draft`, по которым психолог не завершил работу, **автоматически не удаляются**.

Администратору предоставляется:

- фильтр списка групп по статусу и дате создания, позволяющий быстро найти брошенные записи;
- возможность удалить такую группу вручную (soft delete);
- запрет на удаление группы, по которой существует успешный платёж без отметки о возврате — в этом случае показывается предупреждение с требованием сначала обработать платёж.

# 11. Поля группы

`gp_groups`:

- `id`;
- `public_uuid`;
- `owner_id`;
- `status`;
- `disabled`;
- `accept`;
- `free`;
- название;
- описание;
- расписание;
- формат — ссылка на справочник;
- длительность одной встречи — количество минут, integer;
- количество человек — integer;
- пол — ссылка на справочник;
- стоимость одной встречи — целое число в копейках;
- `moderator_comment` — последний комментарий модератора, полная история в `gp_group_status_history`;
- `rejection_reason` — причина отклонения;
- `published_at`;
- `expires_at`;
- `psychologist_deleted_at` — nullable UTC-время скрытия отклонённой группы из кабинета психолога;
- `expiry_warning_sent_at` — дата отправки предупреждения об окончании;
- `placement_days` — фактический срок размещения, зафиксированный на момент активации;
- timestamps;
- soft delete.

`public_uuid` — единственный интеграционный идентификатор группы для связи с `gruppa.info`. Он:

- генерируется автоматически при создании группы как случайный UUID v4;
- уникален;
- после создания не изменяется пользователем или администратором;
- не является внутренним primary key и не раскрывает `gp_groups.id`;
- показывается администратору в карточке группы под понятным названием **«ID группы для gruppa.info»**;
- рядом отображается кнопка **«Скопировать ID»**;
- вручную сохраняется в соответствующей записи группы на основном сайте, например в поле `cabinet_group_uuid`;
- передаётся основным сайтом в кабинет при отправке заявки участника.

Дополнительный внешний ID группы основного сайта в кабинете не хранится: обратная связь по ID каталога для MVP не требуется.

`placement_days` фиксируется из настроек в момент активации, чтобы последующее изменение настройки не искажало историю.

# 12. Статусы группы

## `awaiting_payment`
Ожидает оплаты.

Отображение: **Ожидает оплаты**

## `draft`
Оплата подтверждена либо группа бесплатная, но анкета группы ещё не отправлена.

Отображение: **Черновик**

## `moderation`
Отправлена администратору.

Отображение: **На модерации**

## `revision`
Администратор запросил исправления.

Отображение: **На доработке**

Психолог обязательно видит комментарий администратора и всю историю замечаний.

## `rejected`
Группа отклонена.

Отображение: **Отклонена**

Причина отклонения обязательна и показывается психологу.

## `approved`
Администратор одобрил группу, но ещё не опубликовал её в публичном каталоге.

Отображение: **Одобрена, ожидает публикации**

## `active`
Администратор вручную опубликовал группу в каталоге и нажал «Отметить активной».

Отображение: **Активная**

## `expired`
Срок размещения закончился.

Отображение: **Закончена**

## Матрица допустимых переходов

| Из | В | Кто |
|---|---|---|
| `awaiting_payment` | `draft` | система, по первому доверенному подтверждению WEBPAY |
| `draft` | `moderation` | психолог |
| `moderation` | `approved` | администратор |
| `moderation` | `revision` | администратор, комментарий обязателен |
| `moderation` | `rejected` | администратор, причина обязательна |
| `revision` | `moderation` | психолог |
| `approved` | `active` | администратор |
| `active` | `expired` | система, по расписанию |
| `expired` | `approved` | система, после успешной оплаты продления (см. §16) |

Любой другой переход недопустим и должен приводить к ошибке независимо от того, как он инициирован — через интерфейс, подделанный POST или прямой вызов сервиса.

`disabled=true` используется отдельно для административного отключения группы и не входит в матрицу переходов.

# 13. Модерация группы

Администратор открывает группу и видит:

- данные психолога;
- данные группы;
- информацию об оплате, если группа платная — сумма, `order_number`, `transaction_id`, статус, дата;
- текущий статус;
- полную историю статусов и комментариев.

Действия:

### Одобрить

`moderation → approved`

### Отправить на доработку

`moderation → revision`

Комментарий обязателен. Комментарий сохраняется в историю и не затирает предыдущие.

Психолог редактирует группу и повторно отправляет её:

`revision → moderation`

### Отклонить

`moderation → rejected`

Причина отклонения обязательна, минимальная длина проверяется валидацией.

Если группа платная и по ней есть успешный платёж, интерфейс отклонения показывает напоминание о необходимости ручного возврата и данные платежа.

### Отметить активной

Доступно после ручной публикации в существующем каталоге:

`approved → active`

При этом:

- `published_at = текущее время`;
- `placement_days` = значение из настроек;
- `expires_at = published_at + placement_days`;
- `expiry_warning_sent_at` сбрасывается в null.

Перед нажатием «Отметить активной» администратор видит блок **«Интеграция с gruppa.info»** с `public_uuid` и кнопкой копирования. Интерфейс напоминает убедиться, что этот ID сохранён у соответствующей опубликованной группы на основном сайте. Кабинет не хранит отдельный ID записи основного сайта и не пытается автоматически проверять эту связь в MVP.

# 14. Ограничения редактирования группы психологом

Психолог может редактировать группу в состояниях:

- `draft`;
- `revision`.

Просмотр доступен для всех его групп, кроме soft-deleted и скрытых через `psychologist_deleted_at`.

В `moderation`, `approved`, `active`, `expired` редактирование блокируется, чтобы данные кабинета не расходились с данными, которые проверяет или уже опубликовал администратор.

Удалять психолог может только группы в статусах `draft` и `rejected`, по которым нет успешного неотозванного платежа.

Для `draft` удаление психологом является soft delete. Для `rejected` оно устанавливает
`psychologist_deleted_at` в текущее UTC-время, сохраняя `deleted_at = null` и статус
`rejected`. Группа недоступна во всех маршрутах психолога, включая заявки и
продление, но остаётся в обычных списках, поиске и карточке администратора.
Связанные данные и история сохраняются, переход статуса не создаётся.

Администратор имеет полный доступ независимо от статуса. Он может удалить
группу в любом статусе через подтверждённый soft delete, если нет succeeded-платежа
без `refunded_at`, включая исторические soft-deleted платежи. Удалённая им группа
исчезает из обычного admin-списка. Аудит `group_deleted` содержит текущий статус;
история переходов не меняется. Для active подтверждение требует вручную снять
публикацию на gruppa.info; для approved — проверить и снять её при наличии.
Произвольная ручная смена статуса администратором не предусмотрена, матрица прежняя.

# 15. Срок размещения

Срок размещения начинается **не с оплаты и не с одобрения**, а с момента ручной публикации администратором.

При активации:

`expires_at = published_at + placement_days`

Значение по умолчанию — 30 дней, хранится в настройках.

В форме редактирования существующей группы администратор может исправить
`published_at` и `expires_at`: ввод/показ Europe/Minsk, хранение UTC. Пустые даты
допустимы; если заданы обе, окончание строго позже публикации. Поле `placement_days`
не редактируется. Изменение `expires_at` сбрасывает `expiry_warning_sent_at`,
изменение только `published_at` не сбрасывает его. Сохранение транзакционное,
аудит `group_placement_dates_changed` содержит только старые/новые UTC ISO даты.
Коррекция не создаёт переход статуса: просроченный active обрабатывается обычным
планировщиком. Продление по-прежнему использует снимок `placement_days`.

За N дней до `expires_at` (по умолчанию 3):

- психолог получает email;
- в списке групп появляется заметная отметка: **«До окончания размещения 3 дня»**.

Письмо отправляется только один раз для текущего периода размещения. Признак — `expiry_warning_sent_at`.

После наступления `expires_at`:

`active → expired`

Психолог видит статус **Закончена** и кнопку **«Продлить размещение»**.

Поскольку публикация в каталоге выполняется вручную, автоматическое удаление группы с публичного сайта в MVP не выполняется. Администратор видит такие группы в отдельном фильтре и снимает их с публикации вручную.

# 16. Продление размещения

Продление доступно для групп в статусах `active` и `expired`.

Повторная модерация при продлении **не выполняется**: содержание группы уже проверено.

Тариф продления определяется **в момент начала конкретной попытки продления** по текущему `gp_users.free` владельца группы. Историческое значение `gp_groups.free` на решение о бесплатности/платности продления не влияет.

Если тариф психолога изменился после создания группы или после предыдущего продления, следующая попытка продления использует новое актуальное значение тарифа.

## Бесплатный психолог

1. Психолог нажимает «Продлить размещение».
2. Платёж не создаётся.
3. Применяется логика продления (см. ниже).

## Платный психолог

После подключения WEBPAY Sandbox/production flow:

1. Психолог нажимает «Продлить размещение».
2. Создаётся запись `gp_payments` с типом `extension`, новым уникальным `order_number` и ссылкой на группу.
3. Пользователь перенаправляется на WEBPAY.
4. Browser return/cancel сам по себе продление не применяет.
5. Продление применяется только после первого доверенного подтверждения WEBPAY: валидного нотификатора либо успешного `get_transaction`.
6. Повторный нотификатор/API-check не должен продлить группу второй раз.
7. При неуспешной оплате пользователь может повторить попытку — создаётся новая запись платежа.

Стоимость продления берётся из настроек. В MVP она может совпадать со стоимостью размещения.

## Логика продления

### Группа в статусе `active`

- `expires_at = expires_at + placement_days`;
- статус не меняется, группа остаётся опубликованной;
- `expiry_warning_sent_at` сбрасывается в null, чтобы предупреждение пришло заново перед новым окончанием;
- действия администратора не требуются.

### Группа в статусе `expired`

- группа переходит `expired → approved`;
- `published_at` и `expires_at` не устанавливаются в момент подтверждения оплаты;
- администратор видит группу в списке ожидающих публикации с пометкой «Продление», публикует её в каталоге вручную и нажимает «Отметить активной»;
- при активации даты рассчитываются как при первичной публикации.

Причина: снятие группы с публикации при истечении срока выполняется администратором вручную, поэтому возврат в каталог тоже требует ручного действия. Повторная модерация при этом не производится — администратор только публикует.

Продление группы в статусе `expired` доступно в течение срока, заданного настройкой (по умолчанию 30 дней после `expires_at`). После этого кнопка продления скрывается и психолог создаёт новую группу.

# 17. Заявки участников

Заявка создаётся посетителем на странице конкретной группы основного сайта `https://gruppa.info/`. Основной сайт хранит для опубликованной группы её `public_uuid` из кабинета и после отправки пользовательской формы выполняет server-to-server запрос в API кабинета.

Основной сайт передаёт в приложение:

- `group_uuid` — значение `gp_groups.public_uuid`, сохранённое на основном сайте как интеграционный ID группы;
- фамилию;
- имя;
- телефон.

`psychologist_id` или `owner_id` основной сайт **не передаёт**. Кабинет сам находит группу по `public_uuid`, затем определяет её владельца через `gp_groups.owner_id`. Это исключает противоречивые комбинации «группа одного психолога + ID другого психолога».

Создаётся `gp_group_applications`:

- `id`;
- `group_id`;
- фамилия;
- имя;
- телефон;
- `phone_normalized` — необязательный по смыслу технический ключ поиска (может быть пустой строкой);
- `processed_at`;
- timestamps.

## Правила приёма

Заявка принимается **только для группы в статусе `active`**.

На публичном сайте форма заявки отображается только у опубликованных групп, поэтому в норме нарушение невозможно, однако приложение обязано проверять статус самостоятельно:

- группа не найдена по `public_uuid` → HTTP 404;
- группа найдена, но не в статусе `active` либо `disabled=true` → HTTP 422 с понятным кодом ошибки;
- отказ фиксируется только минимальным техническим логом по правилам §4.10/§18, без полного payload.

Телефон обязателен как строка, непустая после trim и не длиннее 255 символов. Международный формат, `+`/`00`, код страны и количество цифр не требуются. В `phone` сохраняется введённое значение после trim. `phone_normalized` содержит цифры, если поисковый нормализатор может их получить, иначе пустую строку; код страны не додумывается. Локальные номера и произвольный текст принимаются. Поиск работает по исходному телефону и полезному цифровому ключу. Идемпотентность использует непустой ключ, иначе исходный trim-текст.

## Доступ

Психолог:

- видит только заявки принадлежащих ему групп;
- не имеет возможности открыть заявки другого психолога;
- может отметить заявку обработанной;
- может вернуть её обратно в необработанные.

В интерфейсе группы показывается количество новых, обработанных и всех заявок.

## Хранение персональных данных участников

Заявки содержат персональные данные третьих лиц.

- срок хранения заявок задаётся настройкой, по умолчанию 12 месяцев с даты создания;
- scheduled-команда удаляет заявки старше этого срока;
- удаление — окончательное, включая soft-deleted записи;
- команда логирует количество удалённых записей.

# 18. Интеграция с существующим сайтом

Нужно два входящих server-to-server сценария:

1. передача анкеты психолога с основного сайта в кабинет;
2. передача заявки участника со страницы конкретной группы в нужную группу кабинета.

Основной сайт и кабинет находятся на одном домене, но являются отдельными приложениями:

- публичный сайт: `https://gruppa.info/`;
- кабинет: `https://gruppa.info/cabinet/`;
- API кабинета: `https://gruppa.info/cabinet/api/v1/...`.

Форма отправляется backend основного сайта, который выполняет обычный HTTPS POST в Laravel-кабинет. Endpoints публичные: прямые обращения также возможны, доверенная идентичность источника не проверяется. Общий секрет и HMAC не используются; вводить секреты публичного сайта для этих форм не нужно.

## Общие требования

- все интеграционные маршруты располагаются под префиксом версии: `/api/v1/...`; полный production URL начинается с `https://gruppa.info/cabinet/api/v1/...`;
- маршруты исключены из web-middleware и не используют CSRF;
- используется только HTTPS;
- опциональный IP allowlist, отключённый при пустом значении;
- rate limit на каждый маршрут;
- единый формат ответа об ошибке: HTTP-код, машиночитаемый `code`, человекочитаемое `message`, при ошибках валидации — `errors`;
- отклонённые запросы логируются только в минимально необходимом объёме: endpoint, `X-Request-Id`, причина, IP, timestamp и технический код; полное тело анкеты/заявки, документы и секреты в application log не пишутся.

## Публичный протокол запросов

- `INTEGRATION_SECRET`, `INTEGRATION_TIMESTAMP_TOLERANCE`, `X-Timestamp` и `X-Signature` не используются;
- `X-Request-Id` обязателен как несекретный ключ идемпотентности, а не аутентификация;
- кабинет самостоятельно проверяет данные, файлы и бизнес-правила;
- злоупотребления ограничиваются валидацией, rate limiting и опциональными инфраструктурными мерами; это не аутентификация источника и не гарантия отсутствия спама.

## Идемпотентность

Публичный сайт передаёт заголовок `X-Request-Id` — уникальный идентификатор попытки.

Приложение хранит обработанные идентификаторы в MySQL-журнале `gp_integration_requests` и при повторном получении того же `X-Request-Id` возвращает результат первой обработки, не создавая дубликат.

Это защищает от дублей при повторной отправке запроса сайтом по таймауту. Отпечаток учитывает нормализованные поля, значения и порядок обучений, привязку сертификата к позиции, серверные type/name/size/SHA-256 файлов. Изменение данных при том же ID даёт 409; порядок multipart-частей и boundary не влияют. Журнал не хранит payload/PII/файлы.

## Регистрация психолога

Существующий сайт отправляет серверный POST со следующим содержимым:

- ровно одно скалярное multipart-поле `payload`: JSON-объект с полями анкеты напрямую, включая время и версию согласия;
- необязательный JSON-список `trainings`: объекты с четырьмя полями обучения (§6), хотя бы одно содержательное значение, без прикладного лимита количества; старые top-level поля обучения отклоняются;
- `certificate_N` связан с `trainings[N]`; без соответствующего обучения — 422, обучение без сертификата допустимо;
- необязательные плоские файлы `diploma`, `certificate_0`, `certificate_1`, …, `license`, `registration`;
- без manifest/descriptors, клиентских size/SHA-256: метаданные и хеш для идемпотентности вычисляет кабинет;
- по принятому решению сохраняется стандартный PHP/Laravel multipart parsing: неизвестные file fields, неправильные `certificate_N`, неожиданные массивы/структуры и наблюдаемые duplicate/ambiguous structures отклоняются с 422; все видимые Laravel файлы валидируются сервером;
- duplicate multipart field names, схлопнутые PHP до Laravel, нельзя надёжно обнаружить на application layer; это известное ограничение, отдельный raw parser или изменение инфраструктуры не требуются (см. `docs/integration.md`).

Поведение при повторном email описано в §5.

## Связь опубликованной группы с кабинетом

При создании `gp_groups` кабинет автоматически генерирует неизменяемый `public_uuid`.

В admin-карточке группы есть отдельный блок **«Интеграция с gruppa.info»**:

- **ID группы для gruppa.info** — значение `public_uuid`;
- кнопка **«Скопировать ID»**;
- краткая подсказка, что это значение нужно сохранить у соответствующей группы на основном сайте.

При ручной публикации группы администратор копирует этот ID и сохраняет его на основном сайте в отдельном поле группы, рекомендуемое имя — `cabinet_group_uuid`. Поле на основном сайте должно быть nullable до связывания и уникальным среди групп после заполнения, чтобы две публичные страницы случайно не ссылались на одну и ту же группу кабинета. Фактическое имя поля может отличаться, но его смысл фиксирован. В кабинете ID группы основного сайта отдельно не хранится.

## Заявка в группу

Основной сайт после отправки формы посетителем выполняет серверный POST:

`POST https://gruppa.info/cabinet/api/v1/group-applications`

Тело содержит:

- `group_uuid`;
- фамилию;
- имя;
- телефон.

Кабинет:

1. находит `gp_groups` по `public_uuid = group_uuid`;
2. проверяет `status=active`;
3. проверяет `disabled=false`;
4. определяет владельца через `owner_id`;
5. создаёт `gp_group_applications` с найденным `group_id`;
6. после этого заявка автоматически становится доступна только владельцу этой группы и администратору.

ID психолога основной сайт не передаёт.

Поведение, статусы ошибок и доступ описаны в §17.

## Документация

По результатам этапа интеграции готовится отдельный документ для разработчика публичного сайта: production/staging адреса, сохранение `public_uuid`/`cabinet_group_uuid`, формат запросов, public submission flow, идемпотентность, коды ответов и примеры запросов.

# 19. Платежи и интеграция WEBPAY

## 19.1. Провайдер и источник технических требований

Платёжный провайдер MVP — **WEBPAY (webpay.by)**.

Официальная документация: `https://docs.webpay.by/`.

В части provider-specific протокола — URL, названий полей, алгоритмов подписи, формата API и нотификаторов — источником истины является актуальная официальная документация WEBPAY на момент реализации этапа. Бизнес-правила приложения определяются этим ТЗ.

Перед началом Sandbox-этапа разработчик повторно сверяет provider-specific детали с документацией и фиксирует использованные параметры в `docs/webpay.md`.

Для MVP:

- только интернет-эквайринг банковских карт;
- версия платёжной формы WEBPAY — `wsb_version=2`;
- одностадийная оплата;
- возврат выполняется вручную администратором в личном кабинете WEBPAY;
- автоматический refund API не используется;
- ЕРИП, рекуррентные платежи, Apple Pay и другие дополнительные сценарии не реализуются.

Если фактическая конфигурация мерчанта WEBPAY отличается от этих предпосылок, платёжный этап блокируется до согласования, а бизнес-логику самостоятельно не менять.

## 19.2. Sandbox и production

Разработка и основная платёжная приёмка выполняются **только в WEBPAY Sandbox**.

Sandbox:

- платёжная страница: `https://securesandbox.webpay.by/`;
- API/кабинет тестовой среды: `https://sandbox.webpay.by`;
- `wsb_test=1`;
- используются отдельные Sandbox `wsb_storeid`, SecretKey и API credentials.

Production:

- платёжная страница: `https://payment.webpay.by/`;
- API/кабинет: `https://billing.webpay.by`;
- `wsb_test=0`;
- используются production `wsb_storeid`, SecretKey и API credentials.

Переход Sandbox → Production выполняется **только конфигурацией**, без изменения бизнес-кода.

В `.env` минимально предусматриваются:

- `WEBPAY_ENV=sandbox|production`;
- `WEBPAY_STORE_ID`;
- `WEBPAY_SECRET_KEY`;
- `WEBPAY_API_USERNAME`;
- `WEBPAY_API_PASSWORD`.

URL среды и значение `wsb_test` выбираются `WebpayService`/adapter по `WEBPAY_ENV`. Допускается override URL только для автотестов.

Боевые credentials:

- не используются на локальной разработке;
- не используются при основной Sandbox-приёмке;
- не хранятся в Git, Docker image, `compose.yaml`, тестах или документации;
- добавляются непосредственно в production `.env` только на этапе 16 перед запуском.

## 19.3. Production-домен и публичный callback

WEBPAY проверяет домен, с которого пользователь отправляется на production-платёжную страницу. Production-кабинет работает на том же host `gruppa.info` по пути `/cabinet`, без отдельного поддомена.

До production-запуска необходимо подтвердить, что домен `gruppa.info` указан/разрешён в договоре и настройках WEBPAY. Путь `/cabinet` отдельно не считается новым доменом, но все return/cancel/notify URL должны указывать на фактический base path кабинета.

Нотификатор WEBPAY приходит на публичный `wsb_notify_url`; локальный `localhost` недоступен WEBPAY.

Для разработки допускается HTTPS tunnel до локального Docker-приложения. Для финальной Sandbox-приёмки предпочтительно использовать публичный staging с HTTPS.

Нотификатор должен быть доступен на поддерживаемом WEBPAY порту, предпочтительно `443`.

## 19.4. Изоляция WEBPAY-логики

Вся provider-specific логика выносится в отдельный сервис/adapter, например `WebpayService` / `PaymentProviderInterface`.

Контроллеры не формируют подписи и не разбирают WEBPAY-протокол самостоятельно.

Сервис отвечает за:

- формирование полей платёжной формы;
- создание `wsb_seed`;
- формирование `wsb_signature`;
- выбор Sandbox/production URL;
- проверку подписи нотификатора;
- выполнение `get_transaction`;
- проверку и нормализацию ответа;
- преобразование денежных сумм без `float`;
- возврат нормализованного результата доменному payment service.

Adapter должен подменяться fake/test реализацией в автоматических тестах.

## 19.5. Формирование заказа WEBPAY

Для каждой платёжной попытки приложение генерирует уникальный `gp_payments.order_number`, который передаётся как `wsb_order_num`.

Нельзя использовать `transaction_id` как идентификатор создаваемого заказа: `transaction_id` присваивает WEBPAY после проведения операции.

Для WEBPAY protocol v2 подпись заказа формируется строго по официальному алгоритму WEBPAY из значений:

- `wsb_seed`;
- `wsb_storeid`;
- `wsb_order_num`;
- `wsb_test`;
- `wsb_currency_id`;
- `wsb_total`;
- SecretKey;

для `wsb_version=2` — SHA-1, как требует протокол WEBPAY.

Формат суммы, участвующий в подписи, должен быть точно тем же, что передаётся в `wsb_total`. Для вычислений внутри приложения по-прежнему используются только целые minor units; строка WEBPAY с двумя знаками формируется централизованно без `float`.

В платёжную форму передаются необходимые return/cancel/notify URL приложения.

## 19.6. Таблица платежей

`gp_payments`:

- `id`;
- `owner_id`;
- `group_id`;
- `type` — `placement` / `extension`;
- `order_number` — уникальный внешний идентификатор заказа приложения, передаётся в WEBPAY как `wsb_order_num`, строка не длиннее 64 символов, unique; не использовать внутренний auto-increment `id` как публичный номер заказа;
- `transaction_id` — идентификатор транзакции WEBPAY, хранится строкой, nullable до получения от WEBPAY, unique для non-null значений;
- `amount` — целое число в копейках;
- `currency` — по умолчанию `BYN`;
- `status`;
- `paid_at` — дата доверенно подтверждённой успешной оплаты;
- `refunded_at` — дата отметки о выполненном возврате;
- `refund_comment`;
- `provider_response` — последний полезный нормализованный ответ WEBPAY API, json, nullable;
- `last_status_check_at` — nullable;
- `status_check_attempts` — integer default 0;
- timestamps;
- soft delete.

Статусы платежа:

- `created`;
- `pending`;
- `succeeded`;
- `failed`;
- `cancelled`;
- `refunded`.

Допустимые переходы:

- `created → pending`;
- `pending → succeeded | failed | cancelled`;
- `succeeded → refunded`;
- обратные переходы из `succeeded` в `failed` или `cancelled` **запрещены**.

`failed`/`cancelled` устанавливаются только по доверенным данным WEBPAY, а не по самому факту открытия `wsb_cancel_return_url`.

## 19.7. Нотификатор WEBPAY

WEBPAY отправляет server-to-server POST на `wsb_notify_url` независимо от браузерного return.

Требования:

- маршрут исключён из CSRF и пользовательской auth-middleware;
- provider-specific подпись проверяется строго по официальному алгоритму WEBPAY;
- для стандартного POST-нотификатора ожидаемая подпись WEBPAY вычисляется MD5 из простой конкатенации полей в порядке, установленном WEBPAY: `batch_timestamp`, `currency_id`, `amount`, `payment_method`, `order_id`, `site_order_id`, `transaction_id`, `payment_type`, `rrn`, затем SecretKey; поле `card` не запрашивается и не участвует в обычном MVP-сценарии;
- сравнение вычисленной и полученной подписи выполняется `hash_equals`;
- проверяются `site_order_id`/заказ, `transaction_id`, сумма, валюта, `payment_method` и успешный `payment_type` (`1` или `4` согласно WEBPAY);
- для MVP допустимый платёжный метод — карточный интернет-эквайринг (`cc`);
- сумма WEBPAY преобразуется в minor units без `float` и сравнивается с `gp_payments.amount`;
- обработка выполняется в транзакции с `lockForUpdate` по платежу;
- переход платежа и применение эффекта к группе выполняются в одной транзакции;
- повторный нотификатор идемпотентен;
- если платёж уже `succeeded`, повторное успешное подтверждение отвечает WEBPAY корректно, но не применяет эффект повторно;
- неизвестный заказ/transaction, неверная подпись, сумма или валюта не меняют платеж/группу и фиксируются минимальным техническим логом;
- HTTP-ответ WEBPAY формируется согласно официальным требованиям, чтобы уже успешно обработанный повтор не вызывал бесконечных ретраев.

WEBPAY может передавать дополнительные данные, которые приложению не нужны. Полный номер карты не запрашивается и не сохраняется.

## 19.8. Журнал нотификаторов

Создаётся `gp_payment_notifications`:

- `id`;
- `payment_id` — nullable;
- `order_number` — nullable;
- `transaction_id` — nullable;
- `payload` — json с необходимыми provider-полями, без секретов и ненужных карточных данных;
- `signature_valid`;
- `processed`;
- `result` — краткий технический результат обработки;
- `created_at`.

Запись создаётся и для невалидной подписи/неизвестного заказа, если запрос дошёл до endpoint. Это финансовый технический журнал, а не общий application log.

## 19.9. Return/cancel flow и `get_transaction`

`wsb_return_url` и `wsb_cancel_return_url` являются браузерными маршрутами.

На успешном return WEBPAY передаёт идентификатор заказа и `wsb_tid`. Приложение не доверяет им как доказательству оплаты, но использует для серверной проверки.

Если возможно, приложение выполняет `get_transaction` через WEBPAY API:

- Sandbox API — `https://sandbox.webpay.by`;
- production API — `https://billing.webpay.by`;
- используется команда `get_transaction` по `transaction_id`;
- авторизация формируется по официальному формату WEBPAY: username + MD5-представление API password внутри provider adapter;
- подпись ответа WEBPAY проверяется как MD5 от полей `transaction_id`, `batch_timestamp`, `currency_id`, `amount`, `payment_method`, `payment_type`, `order_id`, `rrn` и SecretKey в установленном порядке;
- `transaction_id`, сумма, валюта, метод/тип операции и доступные provider identifiers сверяются с локальным платежом;
- успешный доверенный результат (`payment_type` `1` или `4` согласно WEBPAY) проходит через тот же идемпотентный доменный обработчик, что и нотификатор.

Если WEBPAY API временно недоступен, пользователю показывается состояние «Оплата подтверждается WEBPAY», а платёж остаётся `pending`.

Cancel return не является достаточным доказательством `cancelled`.

## 19.10. Проверка зависших pending-платежей

Нотификатор остаётся основным асинхронным каналом. Постоянный polling всех операций запрещён.

Для платежа, который остаётся `pending` после платёжной сессии, реализуется ограниченная контрольная проверка `get_transaction`:

- первая автоматическая проверка — не ранее чем примерно через 20 минут после начала платёжной попытки;
- при сетевой/временной ошибке допускаются ограниченные повторные проверки с увеличением интервала;
- автоматические повторные попытки прекращаются не позднее чем через 1 час от первой контрольной проверки;
- `last_status_check_at` и `status_check_attempts` обновляются;
- если WEBPAY так и не дал достоверного ответа, платёж остаётся `pending`, а администратор видит его как требующий ручной проверки; автоматически считать его успешным или неуспешным запрещено.

Этот механизм является recovery для потерянного нотификатора/неудачного API-ответа и не считается общей автоматической сверкой всех платежей.

## 19.11. Идемпотентное применение эффекта платежа

Для `placement` первое доверенное подтверждение `succeeded`:

- переводит платёж в `succeeded`;
- заполняет `paid_at`/`transaction_id`;
- переводит связанную группу `awaiting_payment → draft`.

Для `extension` первое доверенное подтверждение:

- переводит платёж в `succeeded`;
- ровно один раз применяет правила §16 к связанной группе.

Нотификатор, return-check, fallback-check и повторные запросы используют **один общий доменный обработчик подтверждения**, поэтому race condition между каналами не может применить продуктовый эффект дважды.

## 19.12. Возврат

Автоматический refund через WEBPAY API в MVP не реализуется.

Фактический возврат выполняет администратор вручную в личном кабинете WEBPAY.

После фактического возврата администратор отмечает его в приложении:

- `succeeded → refunded`;
- `refunded_at`;
- `refund_comment`;
- запись в `gp_audit_log`.

Приложение не должно отображать внутреннюю кнопку «Возврат» так, будто она отправляет деньги: действие называется явно, например **«Отметить возврат выполненным в WEBPAY»**.

## 19.13. Административный доступ

Администратор видит:

- тип платежа;
- `order_number`;

# 24. Прототипирование и статическая вёрстка всех страниц

Отдельный этап разработки абстрактной дизайн-системы/UI-kit отменяется.

Вместо него в начале проекта выполняется **полная статическая frontend-версия будущего приложения на конечном стеке**: Blade + Bootstrap 5 + собственный CSS + минимальный Vanilla JS.

Цель этапа: до начала массового backend CRUD визуально и структурно утвердить весь кабинет, чтобы последующие этапы подключали реальные контроллеры, модели и Form Request к уже готовым Blade-шаблонам, а не проектировали страницы заново.

## 24.1. Принцип реализации

Прототипы — не одноразовые HTML-файлы и не отдельная копия интерфейса.

Требования:

- страницы создаются сразу в финальной структуре `resources/views/...`;
- используются реальные Blade layouts, partials и components;
- prototype routes рендерят **те же Blade-файлы**, которые затем используются production-контроллерами;
- данные для прототипов — fixture/mock arrays/ViewModels, без необходимости реальной БД и бизнес-логики;
- development-only маршруты располагаются под отдельным префиксом, например `/_prototype/...`;
- prototype routes регистрируются только в `local`/`testing` и отсутствуют в production;
- запрещено держать отдельную «статическую» копию HTML, которую позже нужно переносить в Blade;
- формы на прототипном этапе могут быть неактивными/no-op, но должны иметь окончательную структуру полей, labels, help/error areas и кнопок;
- input names по возможности сразу соответствуют будущим Form Request;
- все основные состояния одной страницы показываются отдельными prototype variants;
- после визуального утверждения изменение общей структуры/дизайна страницы выполняется только по отдельной необходимости, а backend-этапы преимущественно подключают данные и действия.

## 24.2. Базовая дизайн-система

Отдельного этапа UI-kit нет, но все прототипы и production-страницы обязаны использовать одну базовую дизайн-систему. Она реализуется непосредственно в общих CSS variables/tokens и Blade-компонентах этапа прототипирования.

### Шрифт

Основной шрифт интерфейса — **Montserrat**.

Требования:

- шрифт хранится локально в `application/public/`, без Google Fonts/CDN;
- подключаются только реально используемые начертания и кириллица;
- основной вес текста — `500`;
- заголовки, кнопки, labels, важные значения и смысловые выделения — `600`;
- `font-display: swap`;
- нельзя подменять Montserrat системным шрифтом на отдельных страницах без отдельного решения.

Точная шкала размеров заголовков/текста утверждается на этапе 3 по прототипам и затем фиксируется в CSS tokens; разные страницы не вводят собственные несогласованные размеры.

### Основная палитра

Обязательные базовые токены:

| Назначение | Цвет |
|---|---|
| Accent | `#FF714A` |
| Accent strong / primary button with white text | `#CC4B2A` |
| Main text | `#3C3834` |
| Surface 1 | `#F5F4F0` |
| Surface 2 | `#EBE9E2` |
| White / main background | `#FFFFFF` |
| White text on dark/primary controls | `#FFFFFF` |

`#FF714A` остаётся главным фирменным акцентом: активные элементы, иконки, декоративные выделения, focus/accent states. Для небольших primary-кнопок с белым текстом используется более тёмный `#CC4B2A`, чтобы сохранить читаемость; визуально он остаётся частью той же оранжевой палитры.

Muted text и border должны быть нейтральными производными от `#3C3834` / `#EBE9E2`, фиксируются едиными tokens на этапе 3 и не подбираются отдельно на каждой странице.

### Служебные состояния

| Состояние | Основной цвет | Светлая подложка |
|---|---|---|
| Success | `#2F7D5A` | `#EAF4EE` |
| Warning | `#9A6817` | `#FFF2D9` |
| Danger / Error | `#C84E42` | `#FBE9E6` |
| Info | `#4F6F8F` | `#EAF0F5` |

Служебные цвета применяются только для семантических состояний и не заменяют фирменный accent. Статус не должен различаться только цветом: badge/alert также содержит текст/иконку или другое однозначное обозначение.

### Скругления и форма элементов

Общий визуальный характер — мягкие, сильно скруглённые формы.

- карточки, крупные панели и модальные окна — до `32px`;
- небольшие контейнеры — ориентировочно `20–24px`;
- кнопки — полностью скруглённые (`border-radius: 9999px` / pill);
- badges, chips, tags — pill;
- однострочные inputs/select и аналогичные controls — максимально скруглённые/pill, если это не ухудшает usability;
- textarea и многострочные блоки — `24–32px`;
- таблицы на desktop могут оставаться структурными, но внешний контейнер/карточка таблицы использует общий radius;
- скругления не задаются случайными значениями на отдельных страницах: используются общие radius tokens.

### Общий frontend foundation

В процессе создания страниц формируется минимальный общий frontend foundation:

- CSS variables/tokens: палитра выше, muted, border, размеры шрифта, line-height, radius, spacing, shadow;
- общие Blade-компоненты: кнопки, input/textarea/select, checkbox/radio, label, validation error, alert, card, status badge, table/list, pagination, modal/confirmation, dropdown, empty state, navbar/header, sidebar/navigation, page header, date/time, money;
- единые состояния normal/hover/focus/disabled/error/success;
- Bootstrap остаётся foundation, собственный CSS подключается после него;
- специализированный компонент создаётся один раз, если он реально нужен нескольким страницам.

Отдельная UI-kit-страница не является обязательным deliverable. Главный deliverable — законченные страницы и их состояния на этой дизайн-системе.

# 27. Scheduler

Laravel Scheduler используется для:

- проверки приближающегося окончания групп и постановки писем в очередь;
- перевода просроченных групп в `expired`;
- удаления заявок участников с истёкшим сроком хранения;
- начиная с этапа 13 — поиска WEBPAY-платежей `pending`, для которых наступило время ограниченной recovery-проверки §19.10, и постановки соответствующей job в очередь.

На production настраивается cron запуска Laravel Scheduler и обработчик очередей.

## Требования к идемпотентности

- обработка каждой группы выполняется в транзакции с `lockForUpdate`;
- для предупреждения об окончании scheduler ставит отдельную job в очередь, но не отмечает письмо отправленным;
- для одной группы и одного текущего периода размещения одновременно может существовать только одна ожидающая/выполняемая job предупреждения; используется уникальный lock/idempotency key, привязанный минимум к `group_id` и текущему `expires_at`;
- повторный запуск scheduler, пока первая job ещё ожидает или выполняется, не создаёт дубликат;
- `expiry_warning_sent_at` проставляется job только после фактически успешной отправки письма;
- если job была поставлена в очередь, но фактическая отправка завершилась ошибкой, `expiry_warning_sent_at` остаётся `null`, а повторная попытка выполняется механизмом очереди;
- после успешной отправки повторные запуски scheduler не создают новое письмо для того же периода размещения;
- если группа активирована так, что до окончания уже меньше порога, письмо отправляется один раз при первом применимом запуске;
- recovery-check WEBPAY не должен превращаться в постоянный polling: выбираются только платежи, удовлетворяющие правилам §19.10;
- для одного платежа одновременно может выполняться только одна status-check job;
- status-check job использует тот же идемпотентный confirmation service, что return и нотификатор;
- команды пишут в лог только агрегированный итог работы: сколько записей обработано/поставлено в очередь, без payment payload и секретов.

# 28. Технические требования

## Индексы

Обязательные индексы:

- `gp_users`: уникальный индекс по технической generated column активного email согласно §5; индексы по `status`, `disabled`, `free`; уникальный `(email, deleted_at)` не использовать;
- `gp_groups`: уникальный `public_uuid`, индексы по `owner_id`, `status`, `expires_at`, составной `(status, expires_at)` для scheduler, составной `(owner_id, status)`;
- `gp_payments`: уникальный `order_number`, уникальный nullable `transaction_id`, индексы по `owner_id`, `group_id`, `status`, `type`, `created_at`;
- `gp_payment_notifications`: индексы по `payment_id`, `order_number`, `transaction_id`, `created_at`;
- `gp_group_applications`: индексы по `group_id`, `processed_at`, составной `(group_id, processed_at)`, индекс по `created_at` для команды очистки;
- `gp_group_status_history`: индекс по `group_id`;
- `gp_audit_log`: составной индекс `(entity_type, entity_id)`, индекс по `actor_id`, индекс по `created_at`;
- `gp_dictionary_items`: составной `(dictionary_id, code)` уникальный.

## Запросы

- все списки используют eager loading, N+1 запросы недопустимы;
- счётчики заявок в списке групп реализуются через `withCount`, а не запросом на каждую строку;
- все списки административной части имеют пагинацию;
- в тестах списков проверяется отсутствие N+1 (подсчёт количества запросов).

## Транзакции

Любая операция, меняющая несколько сущностей одновременно (переход статуса + запись истории, подтверждение WEBPAY + изменение группы, продление + изменение платежа), выполняется в одной транзакции.

Для конкурентно чувствительных операций платеж/группа блокируются `lockForUpdate` в согласованном порядке, чтобы нотификатор и `get_transaction` не применили один эффект дважды.

## Качество кода

- Laravel Pint с зафиксированным конфигом;
- статический анализ (Larastan) на согласованном уровне;
- server-side валидация через Form Request для всех входящих пользовательских запросов;
- авторизация через policies, проверка в контроллерах обязательна;
- provider-specific WEBPAY code не находится в controllers/models;
- prototype routes физически недоступны в production environment.

## Тесты

Помимо тестов, указанных в приёмке этапов, обязательны:

- тесты матрицы переходов статусов: каждый недопустимый переход приводит к ошибке;
- IDOR-тесты для групп, заявок, документов и платежей;
- тест идемпотентности нотификатора WEBPAY;
- тест race/idempotency: нотификатор и `get_transaction` подтверждают одну операцию, продуктовый эффект применяется ровно один раз;
- тест несовпадения суммы/валюты/order number WEBPAY;
- тест неверной подписи нотификатора;
- тест, что browser return/cancel без server confirmation не создаёт `succeeded`;
- тест limited recovery-check зависшего `pending`;
- тесты scheduler с подменой времени (`Carbon::setTestNow`);
- тест уникальности email при наличии soft-deleted записи;
- тест немедленного разлогинивания заблокированного пользователя.

Тесты выполняются на MySQL в Docker-окружении, а не на SQLite, чтобы поведение индексов, generated columns, блокировок и транзакций совпадало с production.

# 29. Безопасность

Обязательно:

- Laravel CSRF для внутренних форм;
- server-side validation всех запросов;
- password hashing стандартными средствами Laravel;
- authorization через middleware / policies;
- психолог не может получить чужую группу через изменение URL;
- психолог не может получить чужую заявку;
- документы анкеты не доступны напрямую через `public/`;
- маршруты WEBPAY notify и внешней интеграции исключены из пользовательской auth и CSRF там, где это требуется server-to-server протоколом;
- подлинность нотификатора WEBPAY проверяется по официальному алгоритму WEBPAY;
- результаты `get_transaction` проверяются по provider signature и сопоставляются с локальным заказом/суммой/валютой;
- `hash_equals` используется для сравнений подписей/секретных контрольных значений, когда формат позволяет;
- WEBPAY SecretKey и API credentials хранятся только в `.env` соответствующей среды;
- production credentials WEBPAY не копируются в локальный Docker и не коммитятся;
- browser return/cancel никогда сам не является основанием для финансового перехода;
- все финансовые эффекты идемпотентны и защищены транзакцией/row lock;
- заблокированный пользователь теряет доступ немедленно, включая открытые сессии (§7);
- rate limit на login, установку пароля и интеграционные маршруты;
- prototype routes доступны только `local`/`testing`;
- production работает с `APP_DEBUG=false`;
- все секреты только в `.env`;
- application logs соблюдают ограничения §4.10.

Особое внимание тестам IDOR: изменение `group_id`, `user_id`, `payment_id` или `application_id` в URL/POST не должно давать доступ к чужим данным.

# 32. Требования к работе Codex

Каждый этап выполнять отдельной задачей.

Для каждого этапа Codex должен:

1. сначала изучить существующий код и актуальный `docs/project-status.md`;
2. не переделывать уже работающие части без необходимости;
3. реализовать только текущий этап;
4. создавать migrations вместо ручных изменений БД;
5. начиная с этапа 4, переиспользовать утверждённые Blade-шаблоны этапа 3 и общие компоненты, не создавать параллельную верстку;
6. если backend-интеграция требует заметного изменения утверждённой страницы — явно отметить это в результате задачи, а не скрыто переработать UI;
7. добавлять server-side validation через Form Request;
8. добавлять authorization через policies;
9. выполнять переходы статусов только через доменные сервисы, не присваивая поля напрямую;
10. оборачивать многосущностные операции в транзакции;
11. для конкурентно чувствительных платежных переходов использовать row locks и единый идемпотентный обработчик;
12. добавлять автоматические тесты для бизнес-критичной логики, включая IDOR и недопустимые переходы;
13. запускать тесты, Pint и Larastan перед завершением;
14. не добавлять Node/npm/Vite;
15. не добавлять новые framework/packages без реальной необходимости;
16. соблюдать repository boundary: production application code находится в `application/`, Docker infrastructure — вне него;
17. не связывать production deployment с Docker;
18. до этапа 13 не выполнять WEBPAY requests и не требовать credentials;
19. на Stages 13–15 использовать только WEBPAY Sandbox;
20. production WEBPAY credentials использовать только на этапе 16 и только через `.env`;
21. provider-specific WEBPAY details сверять с актуальной официальной документацией и держать в adapter/service, а не в controllers;
22. не логировать full request bodies, документы или secrets в нарушение §4.10;
23. обновлять связанную документацию при изменении архитектуры, setup, интерфейсов или поведения; `docs/project-status.md` обновлять в каждом этапе;
24. документация должна описывать только фактически реализованное состояние и не выдавать планируемое за готовое;
25. в конце задачи сообщать:
    - что сделано;
    - какие файлы изменены;
    - какие migrations добавлены;
    - какие тесты/статический анализ запущены;
    - как вручную проверить этап;
    - какие внешние prerequisites/credentials всё ещё отсутствуют или intentionally не используются.

Основной принцип проекта:

**простая Laravel-архитектура без лишней абстракции; Docker только для локального окружения; интерфейс заранее утверждается как набор реальных Blade-шаблонов; бизнес-статусы, авторизация, интеграции и WEBPAY изолированы; Sandbox полностью принимается до появления production credentials.**
