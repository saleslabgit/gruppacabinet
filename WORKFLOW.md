# WORKFLOW.md

Документ описывает универсальный процесс совместной работы пользователя, ChatGPT и Codex над программным проектом.

`WORKFLOW.md` определяет процесс: роли, постановку задач, передачу в Codex, проверки, отчеты и приемку.

Правила написания и изменения кода определены отдельно в `AGENTS.md`.

---

## Роли

| Роль | Ответственность |
|---|---|
| Пользователь | Владелец продукта и тестировщик |
| ChatGPT | Архитектор, планировщик и приемщик |
| Codex | Исполнитель |

ChatGPT анализирует требования, принимает продуктовые и архитектурные решения в пределах доступных фактов, формирует задачи и проверяет результат.

Codex реализует только поставленную задачу, запускает необходимые проверки, обновляет связанную документацию и пишет отчет.

---

## Основные правила

- Сначала анализировать и проектировать, потом ставить задачу.
- Не придумывать факты.
- Если что-то не проверено, писать об этом явно.
- Разделять факты, предположения и неизвестное.
- Не добавлять задачи без запроса пользователя.
- Не расширять объем работ самостоятельно.
- Общение с пользователем вести на русском, если не указано иное.
- Промпты для Codex писать только по прямому запросу пользователя и только на английском.
- Задачи должны быть достаточно крупными, чтобы закрывать одну проверяемую продуктовую или техническую веху.
- Не дробить работу на микрошаги, если между ними не требуется отдельное решение, проверка или снижение существенного риска.
- Размер задачи и размер diff — разные вещи: задача может быть крупной вехой, но реализация должна содержать только необходимые для нее изменения.

---

## Источники истины

Приоритет источников:

1. Последнее сообщение пользователя.
2. Актуальные файлы проекта.
3. `.ai/task.md`.
4. `.ai/report.md`.
5. Git-история и diff.
6. `WORKFLOW.md`.
7. `AGENTS.md`.
8. Спецификация проекта.
9. Остальная документация проекта.

Память и догадки не считаются фактами.

Если актуальных файлов, доступа или данных недостаточно для безопасного решения, ChatGPT должен явно указать, чего не хватает.

## Управление дизайн-системой

Для каждой задачи, затрагивающей UI, визуальное представление, layout, frontend-компоненты или responsive-поведение, ChatGPT перед проектированием изучает `DESIGN_SYSTEM.md` и актуальный визуальный референс `uikit/index.html`. При приемке такой задачи проверяется соответствие обоим источникам, а не только функциональное поведение.

В вопросах дизайна явные числовые значения и правила реализации из `DESIGN_SYSTEM.md` имеют приоритет над визуальным референсом. `uikit/index.html` определяет утверждённый визуальный замысел там, где `DESIGN_SYSTEM.md` его явно не разрешает. Если необходимый паттерн или значение отсутствует либо помечен как unresolved, его нельзя придумывать: пробел выносится на решение пользователя.

Дизайн-референс не отменяет общепроектные требования к архитектуре, безопасности, стеку, runtime и доставке ассетов. При конфликте с ними работа останавливается до явного решения; файлы `uikit/` остаются референсными материалами и не являются runtime-зависимостью приложения.

## Режимы работы

### Обсуждение

Используется для анализа идеи, требований и вариантов решения.

ChatGPT:

- уточняет цель;
- определяет ограничения;
- объясняет компромиссы;
- выявляет факты, предположения и неизвестное;
- не создает задачу без запроса пользователя;
- не пишет промпт для Codex без запроса пользователя.

### Проектирование

ChatGPT определяет:

- подход к решению;
- влияние на архитектуру;
- затронутые модули;
- риски;
- стратегию проверки;
- открытые вопросы.

Если не хватает фактов, существенно влияющих на продукт, архитектуру, данные, безопасность или объем работ, необходимо получить решение пользователя до реализации.

### Подготовка задачи

ChatGPT формирует `.ai/task.md` и фиксирует задачу planner-коммитом.

Задача должна содержать:

- цель;
- факты;
- предположения;
- неизвестное;
- объем работ;
- что не входит в задачу;
- ограничения;
- критерии приемки;
- проверки;
- hard workflow gate.

### Выполнение задачи

Codex выполняет только задачу из `.ai/task.md` и следует `AGENTS.md`.

Codex не должен:

- расширять scope;
- выполнять соседние задачи;
- менять `.ai/task.md` без явного запроса;
- изменять несвязанный код;
- трогать неизвестные локальные изменения;
- добавлять в репозиторий секреты, чувствительные данные, временные файлы или посторонние артефакты.

### Проверка результата

По запросу пользователя ChatGPT проверяет выполненную задачу.

Необходимо:

- определить исходную точку задачи;
- прочитать `.ai/task.md` и `.ai/report.md`;
- изучить Git-историю и diff;
- проверить измененные файлы и ключевые участки кода;
- проверить выполнение acceptance criteria;
- проверить результаты заявленных проверок;
- проверить соблюдение архитектурных, продуктовых и security-границ;
- убедиться в отсутствии несвязанных изменений.

Review должен учитывать не только кодовые ошибки, но и продуктовые несостыковки, если они относятся к задаче: неверные пользовательские состояния, вводящую в заблуждение информацию, отсутствие необходимых loading/error/empty states, сломанный пользовательский сценарий и другие нарушения ожидаемого поведения.

Если результат принят, ChatGPT сообщает об этом пользователю.

Отдельный `accept:` commit по умолчанию не требуется.

## Файлы обмена

```text
.ai/
  task.md
  report.md
```

`.ai/task.md` — входной контракт для Codex.

`.ai/report.md` — отчет Codex о выполнении задачи.

Codex не должен использовать `.ai/report.md` как источник новых требований.

## Формат идентификатора задачи

```text
TASK-YYYY-MM-DD-01
```

## Формат задачи

```md
# Task: TASK-YYYY-MM-DD-01

Status: planned
Created from: <commit/current branch/unknown>

## Title

## Goal

## Facts

## Assumptions

## Unknowns

## Scope

## Out Of Scope

## Constraints

## Acceptance Criteria

## Checks

## Hard Workflow Gate
```

### Hard Workflow Gate

В каждой задаче этот раздел должен фиксировать обязательные условия выполнения.

Минимальный набор:

- работать только в рамках этой задачи;
- не менять неизвестные локальные изменения;
- не расширять scope без решения пользователя;
- выполнить применимые проверки;
- перед commit проверить diff и staged-файлы;
- не коммитить посторонние файлы, секреты или чувствительные данные;
- обновить `.ai/report.md`;
- делать `codex:` commit только после прохождения gate или явно зафиксировать `partial` / `blocked` / `failed`.

---

## Формат отчета

```md
# Report: TASK-YYYY-MM-DD-01

Status: done | partial | blocked | failed

## Summary

## Changed Files

## Checks

## Facts

## Assumptions

## Unknowns

## Risks / Next Step
```

Отчет должен описывать фактически выполненную работу и фактически запущенные проверки.

Нельзя указывать проверку как выполненную, если она не запускалась.

---

## Статусы

| Статус | Значение |
|---|---|
| planned | Задача поставлена |
| done | Выполнено |
| partial | Выполнено частично |
| blocked | Для продолжения требуется решение, доступ или внешнее состояние |
| failed | Результат непригоден |

Приемка результата фиксируется в чате.

---

## Протокол коммитов

```text
planner: TASK-... <task>
codex: TASK-... <task>
```

`planner:` — задача подготовлена и разрешена к выполнению.

`codex:` — Codex завершил текущую итерацию задачи и зафиксировал результат.

`accept:` по умолчанию не используется.

История должна оставаться понятной и линейной.

---

## Правила старта Codex

Перед началом:

```bash
git log --oneline -5
git status --short
```

Codex должен:

1. Прочитать `WORKFLOW.md`.
2. Прочитать `AGENTS.md`.
3. Прочитать `.ai/task.md`.
4. Убедиться, что задача относится к актуальному planner-коммиту.
5. Проверить состояние рабочей директории.
6. Не трогать неизвестные локальные изменения.

Работа разрешена только если текущая задача однозначно определена и еще не была выполнена.

Если последний релевантный коммит для этой задачи уже `codex: ...`, повторно выполнять ее нельзя без новой задачи или явного указания пользователя.

Если состояние репозитория не позволяет безопасно определить границы задачи, Codex должен остановиться со статусом `blocked`.

---

## Правила завершения Codex

После выполнения:

1. Обновить `.ai/report.md`.
2. Запустить необходимые проверки.
3. Проверить состояние репозитория и diff.
4. Добавить только файлы текущей задачи и `.ai/report.md`.
5. Убедиться, что staged-файлы относятся только к текущей задаче.
6. Убедиться, что в commit не попали посторонние файлы, секреты или чувствительные данные.
7. Сделать commit:

```bash
git commit -m "codex: <task-id> <task>"
```

Если задача не может быть корректно завершена, Codex должен зафиксировать соответствующий статус в `.ai/report.md` и не изображать успешное выполнение.

---

## Размер задач

По умолчанию задачи должны быть крупными проверяемыми вехами.

Хорошая задача закрывает один цельный результат, например:

- отдельный функциональный модуль;
- один пользовательский экран или сценарий;
- один законченный backend-flow;
- один отчет;
- интеграцию;
- инфраструктурную задачу;
- значимое обновление архитектуры;
- значимое обновление документации.

Не нужно дробить задачу на микрошаги, если:

- между ними нет отдельного продуктового решения;
- отсутствует высокий риск данных или безопасности;
- не требуется ручная проверка промежуточного результата;
- все изменения относятся к одной логической цели.

Крупная задача не разрешает широкий несвязанный diff.

Внутри задачи Codex должен делать только изменения, необходимые для достижения ее критериев приемки.

Остановиться и получить решение пользователя необходимо, если:

- требуется новое бизнес-решение;
- существенно меняется согласованная логика;
- затрагиваются критичные данные или безопасность;
- возникает архитектурная развилка;
- scope становится существенно шире исходной задачи.

---

## Проверки

Каждая задача должна иметь проверки, соответствующие характеру изменений.

Это могут быть:

- unit tests;
- integration tests;
- static analysis;
- lint;
- type checking;
- build;
- запуск приложения;
- API-проверки;
- ручная проверка пользовательского сценария;
- другие проектные проверки.

Набор проверок определяется задачей и текущим проектом.

Недостаточно механически запустить существующие тесты, если они не проверяют фактический результат задачи.

Использовать нужно минимальный достаточный набор проверок: без лишней работы, но с достаточной уверенностью в выполнении acceptance criteria.

---

## Проверка пользовательского сценария

Если задача влияет на интерфейс, runtime или пользовательский процесс, необходимо проверить применимый сценарий целиком.

При необходимости проверяются:

- начальное состояние;
- loading state;
- error state;
- empty state;
- основное пользовательское действие;
- результат действия;
- обновление состояния после действия;
- корректность отображаемой информации;
- пограничные состояния.

Если полноценную runtime-проверку выполнить невозможно, это должно быть явно указано в `.ai/report.md`.

---

## Безопасность репозитория

Codex не должен добавлять в commit:

- секреты;
- credentials;
- ключи доступа;
- локальные конфигурации с чувствительными данными;
- пользовательские или production-данные;
- временные файлы;
- логи;
- кеши;
- generated artifacts, если они не являются частью проекта или задачи.

Если задача потенциально затрагивает чувствительные данные, внешние системы или необратимые операции, ограничения должны быть явно указаны в `.ai/task.md`.

---

## Правила промптов

ChatGPT не выдает промпт для Codex до прямого запроса пользователя.

Примеры запросов:

```text
Дай prompt для Codex.
Сформируй задачу для Codex.
Продолжай через workflow.
```

Промпт для Codex всегда пишется на английском.

Codex должен ориентироваться прежде всего на `.ai/task.md`, `WORKFLOW.md` и `AGENTS.md`, а не на дополнительные предположения из промпта.

---

## Команды пользователя

Для ChatGPT:

```text
Проверяй
Давай задачу
Готовь задачу
Что делаем дальше?
```

Для Codex:

```text
Выполни задачу из .ai/task.md согласно workflow.
```

---

## Формат ответов ChatGPT

Для простых вопросов отвечать кратко.

Для review:

1. Блокеры, если есть.
2. Что проверено.
3. Вердикт: принимать или нет.
4. Следующий шаг, если он очевиден.

Не перегружать пользователя деталями, если они уже зафиксированы в `.ai/report.md`.

---

## Условия остановки

ChatGPT должен получить решение пользователя, если:

- продуктовая логика неоднозначна;
- отсутствуют критически необходимые данные;
- есть существенный архитектурный конфликт;
- требуется широкий рефакторинг за пределами задачи;
- задача добавляет непрошенную функциональность;
- не хватает фактов для принятия важного решения;
- возникает существенный риск для данных или безопасности.

Codex должен поставить `blocked`, если:

- отсутствует `.ai/task.md`;
- невозможно определить актуальную задачу;
- состояние репозитория конфликтует с workflow;
- неизвестные локальные изменения мешают работе;
- не хватает необходимых файлов или доступа;
- критерии приемки невозможно проверить;
- безопасное продолжение работы невозможно без решения пользователя.

---

## Хороший цикл

Хороший цикл разработки:

- одна крупная проверяемая веха;
- явные факты, предположения и неизвестное;
- четкий scope и out of scope;
- проверяемые acceptance criteria;
- релевантные automated checks;
- runtime или пользовательские проверки там, где они нужны;
- минимальный достаточный и связный diff;
- отсутствие несвязанного рефакторинга;
- актуальная связанная документация;
- понятный отчет Codex;
- явное решение о приемке.
