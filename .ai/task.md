## Title

Simplify public-site intake — remove shared-secret/HMAC integration and use a plain validated public API contract

## Goal

Remove the shared-secret/HMAC authentication protocol from the public-site intake endpoints so the existing public forms can submit to Gruppa Cabinet without provisioning, copying, caching or debugging any integration secret.

The new contract must be deliberately simple:

- no `INTEGRATION_SECRET`;
- no `X-Timestamp`;
- no `X-Signature`;
- no client-computed HMAC;
- no client-computed document SHA-256 manifest;
- `X-Request-Id` remains a non-secret idempotency key generated by the sender;
- strict server-side validation, rate limiting, private document storage and business rules remain authoritative.

This is an explicit product decision: these are public submission forms, so the intake endpoints no longer authenticate the public-site backend as a trusted origin. They are public write endpoints protected by validation, throttling and existing business constraints rather than by a shared secret.

Do not change WEBPAY, login/authentication, password setup, mail, group lifecycle or admin workflows.

## Facts

- Current HEAD is `6a62a7de22e4f93c42ec8383050e6dcbe9e6b4d4`.
- Current routes are:
  - `POST /api/v1/psychologists`;
  - `POST /api/v1/group-applications`.
- Current `AuthenticateIntegration` requires `X-Request-Id`, `X-Timestamp`, `X-Signature` and `INTEGRATION_SECRET`.
- Current HMAC signing has already caused production integration failures even when the public form itself is valid.
- Current psychologist multipart contract signs a manifest containing questionnaire data and document descriptors with client-computed size/SHA-256.
- Current `IntakeData::psychologist` verifies descriptor/file integrity and uses `invalid_signature` for file mismatches.
- Current business validation, private document storage, education-code mapping, psychologist state conflict rules, group UUID lookup, group active/disabled checks, idempotency journal and rate limiting are already implemented.
- The existing public form is public by design. Removing shared-secret origin authentication does not make the form itself private or authenticated; it intentionally changes the API trust model.
- `X-Request-Id` is not a secret and remains useful for safe retries/idempotency.
- No database schema change is expected.

## Assumptions

- The public-site backend will continue to generate a unique `X-Request-Id` for each logical submission and preserve it for retries.
- The public-site backend can send ordinary JSON/multipart requests without cryptographic signing.
- Direct public callers may reach these endpoints; Cabinet must therefore continue to reject invalid data and enforce all server-side business rules.
- Existing endpoint throttling remains appropriate as a baseline anti-abuse control. CAPTCHA/WAF/spam scoring is a separate product concern and is out of scope.
- Optional IP allowlisting may remain available if it does not become required for normal operation and requires no secret/key provisioning.

## Unknowns

- Production traffic volume and whether the current per-endpoint rate limit will later need tuning.
- Whether additional anti-spam measures will be desired after real traffic is observed.
- The public-site code is outside this repository, so its final deployment is not part of this Codex task.

## Scope

### 1. Remove HMAC/shared-secret authentication

Replace the current signing middleware behavior so normal intake requests do not require or inspect:

- `INTEGRATION_SECRET`;
- `X-Timestamp`;
- `X-Signature`;
- HMAC signing text;
- timestamp tolerance.

Remove obsolete secret/timestamp configuration and documentation.

Keep `X-Request-Id` required and validated with the existing safe syntax unless a failing framework test proves a narrow compatibility correction is necessary.

Keep content-type validation and rejection of query parameters.

If `INTEGRATION_ALLOWED_IPS` is retained, it must remain optional and disabled by an empty value. It must not be required for the normal public-form flow.

Rename/refactor `AuthenticateIntegration` if needed so class/file naming no longer claims authentication that no longer exists.

### 2. Simplify psychologist multipart contract

Change `POST /api/v1/psychologists` to accept:

- exactly one scalar multipart field named `payload`;
- `payload` is a JSON object containing the questionnaire fields directly;
- zero or more conventional flat file fields:
  - `diploma`;
  - `certificate_0`, `certificate_1`, ...;
  - `license`;
  - `registration`.

Do not require a client-generated `documents` manifest.
Do not require client-generated file size or SHA-256 values.
Do not require client-side document descriptors.

Cabinet must derive document metadata itself from the actual uploaded files:

- document type from the allowed field name/prefix;
- safe original name from the actual upload;
- byte size from the actual upload;
- MIME from server-side detection;
- SHA-256 internally only if still useful for semantic idempotency/fingerprinting, not as a client contract.

Unknown/duplicate/invalid file field patterns must return a safe 422 validation error.

Preserve the existing allowed document types and storage mapping:
- diploma;
- certificate;
- license;
- registration.

Preserve current private storage behavior and current configured max size/MIME validation.

Do not make document fields newly mandatory at the Cabinet API layer in this task; preserve the current API ability to submit zero documents. The public site's own form may require its current documents.

### 3. Preserve questionnaire business contract

Preserve current questionnaire fields, normalization and bounds, including:

- required email;
- required personal-data consent timestamp/version;
- optional names/phone;
- education_type_code mapping;
- training fields;
- license fields;
- group-leading experience text;
- groups conducted count;
- confirmation booleans.

Keep the current pending/rejected/approved/disabled/deleted conflict matrix and existing protected-field rejection.

No lifecycle, tariff, access, password or approval behavior may change.

### 4. Preserve group-application contract

`POST /api/v1/group-applications` remains ordinary JSON with only:

- `group_uuid`;
- `last_name`;
- `first_name`;
- `phone`.

Remove HMAC/timestamp requirements from this endpoint too.

Preserve:

- immutable public UUID lookup;
- active + not-disabled requirement;
- owner derivation from the matched group;
- participant phone normalization;
- protected-field rejection;
- current success/error semantics.

### 5. Idempotency and request IDs

Keep the existing integration journal and semantic idempotency behavior.

`X-Request-Id` remains required, non-secret and case-sensitive under the existing syntax.

Same request ID + same semantic content must return the original response without duplicate effects.
Same request ID + changed semantic content must remain 409 `idempotency_conflict`.

For psychologist files, semantic fingerprinting must be based on server-observed file metadata/content, not caller-supplied hashes.

### 6. Error semantics

Remove authentication-only errors that are no longer applicable:

- `missing_timestamp`;
- `invalid_timestamp`;
- `expired_timestamp`;
- `missing_signature`;
- `invalid_signature`;
- `integration_unavailable` due to missing secret.

File upload mismatches/invalid fields/content must become clear 422 validation errors, not 401 authentication errors.

Keep safe JSON errors and redacted technical logging. Do not log submitted PII, file bytes, raw payloads, secrets or SQL details.
